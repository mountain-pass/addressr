# OpenSearch and Deploy State

Current production search topology, the SigV4/health/cutover mechanics, and the migration playbook. Split from `what-you-need-to-know.md` 2026-07-28 (Tier-3 budget).

- **Migrating OpenSearch again? Read `docs/OPENSEARCH-MIGRATION-PLAYBOOK.md` FIRST.** It distills the blue/green migration into a reusable, gated checklist + the expensive learnings. Two full runs are now complete: 1.3.20→2.19 (Phase 1, 2026-07-10) and 2.19→3.5 (Phase 2, 2026-07-14). Key ones: sizing is empirical — re-measure warm parity on the new engine (3.5 held parity at m6g.large × 2, but don't assume for the next major); and the cutover risk-gate wants the full-primary-concurrency scenario _exercised_ pre-cutover, not just read-shadowed — run k6 against the candidate domain AS primary (local server → candidate over SigV4) to lower the scorer's likelihood honestly rather than forcing a bypass.
- **Two backends behind RapidAPI**: `backend.addressr.io` and `backend2.addressr.io`, round-robin load balanced. A Cloudflare Worker (`cool-bush-ca66`) proxies requests from addressr.io and Uptime Robot, injecting a RapidAPI API key.
- **Production OpenSearch is 3.5 on the `addressr6` domain** as of the **2026-08-02 ADR-041 cutover** (commit `33e6c04`); `addressr5` is retained WARM and fully populated as the rollback target, so rollback is a one-line `ELASTIC_HOST` flip, NOT the hours-long rebuild-from-G-NAF that ADR-035 was stuck with. Do not decommission `addressr5` — the runbook's rollback exercise has not been run. The nine quarterly `update-{state}.yml` crons and `populate-search-domain.yml` now default to `target: v4` (`gha-v4-loader`), and the writer path is decoupled from `ELASTIC_HOST` since ADR-034 — flipping the read path cannot retarget a loader. HISTORICAL, for provenance: before 2026-08-02 the sole domain was `addressr5` (m6g.large.search × 2, IAM/SigV4 per ADR 033) following the **2026-07-14 cutover + decommission** (ADR 035 Phase 2), when `addressr5` was the SOLE remaining domain — both `addressr3` (v1/1.3.20, decommissioned 2026-07-11) and `addressr4` (v2/2.19, decommissioned 2026-07-14) are gone. Rollback is now rebuild-from-G-NAF (hours), NOT an instant flip to a warm standby — the accepted ADR-035 Option C trade. The 9 quarterly `update-{state}.yml` crons all target `v3` over GitHub-OIDC/SigV4 (`gha-v3-loader` role). **The 2.19 leg is retained ONLY in the `release.yml` CI matrix** (`['2.19.5','3.5.0']`) as a code-compatibility + regression target until AWS EOLs 2.19 — it is not running infrastructure. In-cutover zero-outage still holds via the EB rolling deploy + `/health` auto-rollback.
- **The EB primary SigV4 config EMPTIES `ELASTIC_USERNAME`/`ELASTIC_PASSWORD`, not just sets `ELASTIC_AUTH_MODE=sigv4`.** `buildClientNode` (`src/client-node-url.js`) omits embedded creds only when username is empty, giving the credential-less node URL the SigV4 signer wraps. Leaving basic creds set alongside sigv4 is an untested config. The cutover EB block: `ELASTIC_HOST=module.opensearch_v2.endpoint`, `ELASTIC_AUTH_MODE=sigv4`, `ELASTIC_REGION=ap-southeast-2`, `ELASTIC_USERNAME=""`, `ELASTIC_PASSWORD=""`.
- **`/health` now pings OpenSearch (503 when unreachable) — a static health check silently breaks zero-outage auto-rollback.** Pre-2026-07-10 `/health` returned 200 without touching the backend, so a misconfigured backend cutover would pass health, roll out fleet-wide, and NOT trigger EB's `RollbackLaunchOnFailure`. `src/es-health.js` (`checkEsHealth`/`checkEsHealthCached`) now `ping()`s the app's `globalThis.esClient`; 503 → EB marks unhealthy after `UnhealthyThreshold=5 × 10s ≈ 50s` → auto-rollback. `HEALTH_ES_PROBE=off` reverts to always-200 (ops kill-switch); a ~5s TTL cache bounds anonymous ping-amplification (`/health` is on the ADR 024 unauth allowlist). General lesson: a deploy-gating health check MUST exercise the dependency it's protecting, or the auto-rollback is theatre.
- **A cutover repoints the SERVING path but you must ALSO repoint every WRITE/refresh consumer.** The 2026-07-10 v2 cutover flipped the EB read path to v2 but the 9 quarterly loader crons kept writing v1 — production read v2 while v2's data silently froze and v1 (unread) kept getting fresh data. The architect caught this before the v1 decommission. When cutting over a backend, enumerate ALL consumers (serving reads, loaders/refreshers, dashboards, alarms), not just the request path.
- **OpenSearch 2.19 needs replicas=0 + larger EBS for a from-scratch bulk load on t3.small.** The 2.19 engine uses ~1.7× the disk-per-doc of 1.3.20; a from-scratch 16.9M-doc load node-drops (and can silently delete the index — P035) on t3.small×2/12GB. Load with a `number_of_replicas: 0` index template + 20GB EBS, then set replicas=1 after the load and let the replica build to green. The t3.small class SERVES 16.8M fine — the wall is the from-scratch load pattern, not steady-state serving.
- **The SigV4 read-shadow mirror adds only ~0.44ms p95 to the primary thread.** Measured 2026-07-08 (2000 warmed iters): shadow-off p95 0.001ms, shadow-on-SigV4 p95 0.438ms. `mirrorRequest` is fire-and-forget and SigV4 signing runs in the async connection layer AFTER it returns, so signing barely touches the synchronous primary path — this is why the ADR 031 ≤1ms invariant holds with SigV4 on. Re-run this micro-measure (more reliable than a k6 delta against a hundreds-of-ms baseline) if the shadow client changes.
- **Edge caching MASKS a backend cutover, in both directions.** During the 2026-08-02 rollback drill the EB environment had already flipped to v3 and was Ready/Green, yet the canonical verification query `55 Pyrmont Bri` kept returning the v4 result for several minutes because the response was cached at the edge (`cf-cache-status` on the RapidAPI/Cloudflare path). Reading that, the first conclusion was "the flip did not take effect" — wrong, and in a real incident it is the conclusion that makes you flip again or roll further back. **Verify a cutover with a query that has never been requested**, or add a cache-buster. A never-before-seen partial like `12 Pyrmont Bri` returned 0 immediately and gave the true answer. Corollary: `/health` cannot discriminate either, since it is a `ping()` that goes green against whichever domain is wired.
- **The rollback path is EXERCISED, not assumed — and it costs 6m36s.** The 2026-08-02 drill flipped `ELASTIC_HOST` to v3 and back, discharging ADR-029's "rollback verified to complete within 10 minutes end-to-end" criterion that had sat open and unmeasured across three migrations. Measured push-to-EB-updated: 6m36s. Two things it exposed: v3 is **no longer fed** by the quarterly loader (repointed to `gha_v4_loader` at the cutover), so every G-NAF refresh makes a rollback serve staler data — a second clock on the rollback net independent of decommission; and the edge-cache trap above. Before the drill, this project had surrendered the warm-standby net **twice** without ever exercising it (v1 deleted 2026-07-11, v2 2026-07-14, each an "accepted trade"), so "we'll test it later" had a 0-for-2 record.
- **`phrase_prefix` scoring depends on WHICH SHARD a document landed on, and `dfs_query_then_fetch` does not fix it.** The clause expands the final query token against the per-shard term dictionary, then BM25 sums IDF across EVERY expansion. Two documents that are equally good matches score differently because their shards hold different word lists. Measured 2026-08-02 on `63 GEOFFREY RD CHITTAWAY POINT`: the range doc's shard also held `POINTERS`, giving it a 9th expansion where the exact doc got 8; that one rare term contributed 12.75 of idf, which was the ENTIRE 61.171-vs-58.268 margin. DFS is the textbook remedy for cross-shard scoring skew and is INEFFECTIVE here (tested, byte-identical results) because the expansion SET is built per-shard before DFS gathers statistics. Pre-exists ADR-041 and is present on the old analyzer identically — ADR-041 only compressed absolute scores ~5x, so constant noise crossed a threshold. Tracked as P078.
- **In a Lucene `_explain`, the number after `in` is an internal doc ID, not a document count.** `weight(sla:63 in 1203037)` means Lucene doc 1203037, NOT "1203037 documents contain this term". Misreading it as a doc count produced a confident, wrong cross-shard-IDF hypothesis that survived a full test cycle before `dfs_query_then_fetch` falsified it. The real term statistics are in the nested `idf, computed as log(1 + (N - n + 0.5) / (n + 0.5))` block, where `n` and `N` are labelled.
- **Two OpenSearch indices**: `addressr` (addresses, ~15M docs) and `addressr-localities` (localities, ~16k docs). Both use the same custom analyzer pipeline. Locality postcodes are derived from ADDRESS_DETAIL during loading (ADR 022).
