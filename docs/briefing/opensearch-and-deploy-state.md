# OpenSearch and Deploy State

Current production search topology, the SigV4/health/cutover mechanics, and the migration playbook. Split from `what-you-need-to-know.md` 2026-07-28 (Tier-3 budget).

- **Migrating OpenSearch again? Read `docs/OPENSEARCH-MIGRATION-PLAYBOOK.md` FIRST.** It distills the blue/green migration into a reusable, gated checklist + the expensive learnings. Two full runs are now complete: 1.3.20→2.19 (Phase 1, 2026-07-10) and 2.19→3.5 (Phase 2, 2026-07-14). Key ones: sizing is empirical — re-measure warm parity on the new engine (3.5 held parity at m6g.large × 2, but don't assume for the next major); and the cutover risk-gate wants the full-primary-concurrency scenario _exercised_ pre-cutover, not just read-shadowed — run k6 against the candidate domain AS primary (local server → candidate over SigV4) to lower the scorer's likelihood honestly rather than forcing a bypass.
- **Two backends behind RapidAPI**: `backend.addressr.io` and `backend2.addressr.io`, round-robin load balanced. A Cloudflare Worker (`cool-bush-ca66`) proxies requests from addressr.io and Uptime Robot, injecting a RapidAPI API key.
- **Production OpenSearch is 3.5** (AWS managed, `addressr5` domain, m6g.large.search × 2, IAM/SigV4 per ADR 033) as of the **2026-07-14 cutover + decommission** (ADR 035 Phase 2). `addressr5` is the SOLE remaining domain — both `addressr3` (v1/1.3.20, decommissioned 2026-07-11) and `addressr4` (v2/2.19, decommissioned 2026-07-14) are gone. Rollback is now rebuild-from-G-NAF (hours), NOT an instant flip to a warm standby — the accepted ADR-035 Option C trade. The 9 quarterly `update-{state}.yml` crons all target `v3` over GitHub-OIDC/SigV4 (`gha-v3-loader` role). **The 2.19 leg is retained ONLY in the `release.yml` CI matrix** (`['2.19.5','3.5.0']`) as a code-compatibility + regression target until AWS EOLs 2.19 — it is not running infrastructure. In-cutover zero-outage still holds via the EB rolling deploy + `/health` auto-rollback.
- **The EB primary SigV4 config EMPTIES `ELASTIC_USERNAME`/`ELASTIC_PASSWORD`, not just sets `ELASTIC_AUTH_MODE=sigv4`.** `buildClientNode` (`src/client-node-url.js`) omits embedded creds only when username is empty, giving the credential-less node URL the SigV4 signer wraps. Leaving basic creds set alongside sigv4 is an untested config. The cutover EB block: `ELASTIC_HOST=module.opensearch_v2.endpoint`, `ELASTIC_AUTH_MODE=sigv4`, `ELASTIC_REGION=ap-southeast-2`, `ELASTIC_USERNAME=""`, `ELASTIC_PASSWORD=""`.
- **`/health` now pings OpenSearch (503 when unreachable) — a static health check silently breaks zero-outage auto-rollback.** Pre-2026-07-10 `/health` returned 200 without touching the backend, so a misconfigured backend cutover would pass health, roll out fleet-wide, and NOT trigger EB's `RollbackLaunchOnFailure`. `src/es-health.js` (`checkEsHealth`/`checkEsHealthCached`) now `ping()`s the app's `globalThis.esClient`; 503 → EB marks unhealthy after `UnhealthyThreshold=5 × 10s ≈ 50s` → auto-rollback. `HEALTH_ES_PROBE=off` reverts to always-200 (ops kill-switch); a ~5s TTL cache bounds anonymous ping-amplification (`/health` is on the ADR 024 unauth allowlist). General lesson: a deploy-gating health check MUST exercise the dependency it's protecting, or the auto-rollback is theatre.
- **A cutover repoints the SERVING path but you must ALSO repoint every WRITE/refresh consumer.** The 2026-07-10 v2 cutover flipped the EB read path to v2 but the 9 quarterly loader crons kept writing v1 — production read v2 while v2's data silently froze and v1 (unread) kept getting fresh data. The architect caught this before the v1 decommission. When cutting over a backend, enumerate ALL consumers (serving reads, loaders/refreshers, dashboards, alarms), not just the request path.
- **OpenSearch 2.19 needs replicas=0 + larger EBS for a from-scratch bulk load on t3.small.** The 2.19 engine uses ~1.7× the disk-per-doc of 1.3.20; a from-scratch 16.9M-doc load node-drops (and can silently delete the index — P035) on t3.small×2/12GB. Load with a `number_of_replicas: 0` index template + 20GB EBS, then set replicas=1 after the load and let the replica build to green. The t3.small class SERVES 16.8M fine — the wall is the from-scratch load pattern, not steady-state serving.
- **The SigV4 read-shadow mirror adds only ~0.44ms p95 to the primary thread.** Measured 2026-07-08 (2000 warmed iters): shadow-off p95 0.001ms, shadow-on-SigV4 p95 0.438ms. `mirrorRequest` is fire-and-forget and SigV4 signing runs in the async connection layer AFTER it returns, so signing barely touches the synchronous primary path — this is why the ADR 031 ≤1ms invariant holds with SigV4 on. Re-run this micro-measure (more reliable than a k6 delta against a hundreds-of-ms baseline) if the shadow client changes.
- **Two OpenSearch indices**: `addressr` (addresses, ~15M docs) and `addressr-localities` (localities, ~16k docs). Both use the same custom analyzer pipeline. Locality postcodes are derived from ADDRESS_DETAIL during loading (ADR 022).
