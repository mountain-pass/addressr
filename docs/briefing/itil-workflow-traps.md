# ITIL Workflow Traps

Problem/ADR lifecycle traps: capture-time anchoring, README drift halts, Confirmation wording, and parking upstream-blocked tickets. Split from `agent-and-workflow-patterns.md` 2026-08-02 (Tier-3 budget rotation).

- **AFK work-problems iter briefings can carry ANOTHER ticket's evaluator caveat — verify against `docs/problems/README.md` Review notes before acting.** The 2026-07-19 P054 iter was dispatched with a CLOSE-CANDIDATE-WITH-CAVEAT citing "driver P007 closed; 3 of 8 tasks; ADR-026 fix in v2.3.0" — all of which describes P015 (see README Review notes), not P054. Acting on the briefing without re-deriving from the ticket file + README would have closed an unfixed upstream defect. Cheap check: the README "Caveated CLOSE-CANDIDATEs" list is authoritative for which ticket owns which caveat.
- **Orchestrator-supplied `persona=` / `jtbd=` values at capture are usually the PLUGIN home-repo enum, not this repo's corpus — always validate before writing them into a ticket.** This repo's personas are `addressr-maintainer / ai-assistant-user / data-quality-analyst / self-hosted-operator / web-app-developer`, and its jobs are JTBD-001/002/003 (web-app-developer), JTBD-100/101 (data-quality-analyst), JTBD-200/201/202 (self-hosted-operator), JTBD-400 (addressr-maintainer). The `agent-plugins` home repo uses `developer / plugin-developer / tech-lead / plugin-user` with JTBD-001 "enforce governance" and JTBD-006 "AFK". The IDs **collide with different meanings**: this repo's JTBD-001 is "search autocomplete addresses", nothing to do with governance. Governance and tooling tickets here anchor to `addressr-maintainer` / `JTBD-400`. Check with `ls -d docs/jtbd/*/ | xargs -n1 basename` before accepting supplied values — this is the P383 adopter-portability rule. Recurred on all three captures of the 2026-07-26 iter (P064/P065/P066 arrived with `plugin-developer` + JTBD-001/JTBD-101), so the leak is systemic to the orchestrator's capture briefing.
- **`/wr-itil:capture-problem` Step 0 halts on pre-existing committed README drift (P041) — even drift the skill itself produced on a prior invocation.** capture-problem deliberately defers README refresh per the lightweight-capture contract (ADR-032); a subsequent capture in the same session then hits the Step 0 halt because the prior capture's deferred refresh is the "pre-existing drift". The override path works (user says "capture anyway"), and `/wr-itil:reconcile-readme` resolves the drift cleanly, but the friction defeats the lightweight-capture design intent.
- **ADR Confirmation wording for problem-lifecycle transitions: tie to criteria, not acceptance.** The `/wr-itil:manage-problem` skill auto-transitions Open → Known Error when root cause + workaround + fix strategy are documented — usually at ADR **proposal**, not acceptance. ADR 029's Confirmation says "P028 transitions on acceptance of this ADR" but the transition happened at proposal. Future ADRs: phrase as "once root cause and fix strategy are documented (i.e. at proposal of this ADR)" to avoid the drift.
- **Parking an upstream-blocked ticket whose upstream issue was filed at the current lifecycle state: reconcile-and-skip the `/wr-itil:update-upstream` dispatch.** The manage-problem Step 7b advisory tells you to post a lifecycle comment on every transition of a `## Reported Upstream` ticket, but when the filing already communicated the confirmed root cause, the comment restates prior as new (the P060 defect, parked upstream as agent-plugins#369). Established pattern, applied on the P053, P054, and P056 parks: re-verify the breach live at park time, record "reconciled-and-skipped per P060" in the `## Parked` section + commit message, post nothing.
