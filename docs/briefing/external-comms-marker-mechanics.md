# External-Comms Gates and the Decisions Compendium

The external-comms / voice-tone / risk commit gates (marker-hash-exact), plus the `docs/decisions/README.md` compendium generator traps. Split from `what-will-surprise-you.md` 2026-07-28 (Tier-3 budget).

- **The external-comms gate cannot clear `gh issue create --body-file` — use the quoted-heredoc `--body "$(cat <<'EOF' ... EOF)"` form.** The gate hashes the body it extracts from the command text to match the reviewer's marker; for `--body-file` it extracts an EMPTY draft (gate source: "When absent (npm publish, --body-file...) DRAFT=''"), while the deny message tells you to have the reviewer wrap the full body in `<draft>` — the two keys can never match, so the deny loops forever. The heredoc `--body` form is extracted verbatim and matches a full-body review marker on the first retry. Hit 2026-07-19 filing agent-plugins#368 (two wasted reviewer dispatches before reading the hook source). Same marker-key-mismatch family as the P048 hash-exactness friction (parked, upstream #361). RECURRED 2026-07-20 filing #370, and AGAIN 2026-07-26 filing #395 (third occurrence) — this file is NOT injected into AFK `claude -p` iter subprocesses. Until migrated, AFK iters should grep this file for the relevant gate/tool surface before external-comms work. **Corollary observed 2026-07-26**: editing the draft AFTER a reviewer PASS invalidates the marker hash and re-blocks, and the two gates invalidate independently — a risk-gate re-review does not restore the voice-tone marker. Freeze the draft before dispatching either reviewer. Also: both gates fail CLOSED when handed a `/tmp` path instead of an inlined `<draft>` block (the reviewer cannot read outside the working dir), costing a full round-trip; always inline.
- **The external-comms commit-message gate extracts and hashes only the FIRST `-m` value.** `external-comms-gate.sh` (wr-risk-scorer 0.17.0) `break`s on the first `-m`/`--message` regex match — it does NOT join across multiple `-m` flags. So a multi-`-m` `git commit` gets only the SUBJECT line hashed, while the reviewer (which you hand the full `<draft>`) hashes the whole message → different marker keys → permanent deny-after-PASS. Fix: review the full message, then commit with a SINGLE `-m` holding the entire multi-line body (real newlines, no interior `"`) so the gate's `-m "([^"]*)"` capture matches the reviewed draft. Corollary gap: body paragraphs of a multi-`-m` commit are never leak-scanned. Hit 2026-07-24 committing the P062 park (two denied attempts before reading the hook source). **Corollary, 2026-07-26 (three more denies):** the gate hashes the LITERAL text of the `-m` argument as it appears in the bash command, not the string the shell finally passes to git. So a single `-m` is necessary but not sufficient — (a) any apostrophe escaped as `'"'"'` leaves that seven-character sequence in the hashed text while the reviewer saw a plain `'`, and (b) `-m "$(cat msg.txt)"` hashes the literal `$(cat msg.txt)`. Both produce a permanent deny-after-PASS that looks identical to a stale marker. Cheapest fix: **write the commit message apostrophe-free** and pass it as one single-quoted `-m`, so the shell literal and the reviewed draft are byte-identical.
- **One external-comms review per draft, with the `SURFACE:` + `<draft>` structure — a batched multi-draft review produces NO marker and cannot clear any gate.** The PostToolUse mark hook derives the marker key via `derive_external_comms_key_from_prompt`, which regexes a line-anchored `^SURFACE: <name>` plus one `<draft>...</draft>` block, then hashes `sha256(normalize(draft) + '\n' + surface)`. A prompt carrying four drafts and no `SURFACE:` line yields an empty key, so even a PASS marks nothing. Both evaluators (`wr-risk-scorer:external-comms` and `wr-voice-tone:external-comms`) must each be dispatched per draft, SYNCHRONOUSLY (`run_in_background: false` — a backgrounded reviewer never fires its mark hook, P402). Surface names come from the gate's own command matcher: `gh-issue-create`, `gh-issue-comment`, `gh-issue-edit`, `gh-pr-create`, `gh-pr-comment`, `gh-api-security-advisories`, `npm-publish`, `git-commit-message`, `changeset-author`. Any edit to the body after review changes the hash, so both evaluators must be re-run on the exact final text.
- **The external-comms commit-message marker hashes the VERBATIM full message including the `Co-Authored-By` + `Claude-Session` trailers.** Re-running `wr-risk-scorer:external-comms` on a refined message only clears the gate if you review the EXACT final text (trailers included); otherwise the commit re-blocks on a hash mismatch. When the message changes at all (even scrubbing one figure), re-review the complete final message before retrying `git commit`. (Root cause confirmed at the v0.17.0 hook source 2026-07-19 — `sha256(full normalized message + surface)`, only whitespace-class normalization, no trailer carve-out; P048 parked upstream-blocked on windyroad/agent-plugins#361.)
- **Commits landed via `wr-risk-scorer-restage-commit` skip the git-commit-message external-comms review entirely** — the gate's surface regex matches only literal `git commit`, and the helper runs it inside its script body where the PreToolUse hook can't see it. Don't rely on the gate to catch leaks in helper-committed messages; review externally-facing message content yourself (the pipeline commit scorer partially compensates but is not the per-message verdict agent). Ticketed as P058; fix belongs upstream in `@windyroad/risk-scorer`.
