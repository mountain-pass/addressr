# Changesets and the Release Flow

How a release actually happens: changesets, the two manual approvals, the `published` gate, and `release:watch`'s false negatives. Split from `releases-and-ci.md` 2026-08-02 (Tier-3 budget rotation).

- **Releasing needs a manual GitHub Actions approval both times.** The changesets release PR (`changeset-release/master`, "chore: release") has its CI runs gated as `action_required` — a human must approve them in the Actions UI before they run, so `release:watch` stalls waiting for a `build` check that never appears. Approve via the API before merging: `gh api -X POST repos/mountain-pass/addressr/actions/runs/<run_id>/approve` (the run shows `conclusion=action_required` in `gh run list --branch changeset-release/master`). The post-merge Release run on `master` runs automatically (no approval). Hit on both v3.0.0 (#505) and v3.0.1 (#506).
- **The changesets release flow is gated on `steps.changesets.outputs.published == 'true'`.** Rollback without a working changeset requires adding a trivial patch changeset to trigger a fresh deploy — there is no `workflow_dispatch` shortcut. Keep `gh secret delete` + one-line changeset as the documented rollback for env-var-driven features.
- **`release.yml`'s `Deploy new version` step is gated on `steps.changesets.outputs.published == 'true'`** — `workflow_dispatch` alone doesn't fire `terraform apply`. Every infra-only deploy event must bundle a `.changeset/*.md` (patch bump suffices). ADR 029 Phase 1 ships v2.4.1 (provision), v2.4.2 (tag fix), v2.4.3 (UA fix), v2.4.4 (uppercase fix) so far — each apply event = a release.
- **Addressr releases via the changesets GitHub Action triggered by `git push origin master`**, not via local `npm publish` or `changeset publish`. Those commands run inside the release workflow, not on the developer's machine. Release-gating (pre-release risk checks, voice/tone review of release notes, changeset presence verification) must happen at the push step, not at the publish command. See P021 for the planned pre-push risk blocking hook.
- **`release:watch` script may falsely report "no new version published" even when publish+deploy+smoke tests all succeed.** Verify via `gh run view` logs or npm registry if in doubt.
