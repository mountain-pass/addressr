# Search Relevance and Scoring

BM25 / analyzer internals behind ranking behaviour, and how to read the evidence correctly. Split from `opensearch-and-deploy-state.md` 2026-08-02 (Tier-3 budget rotation).

- **`phrase_prefix` scoring depends on WHICH SHARD a document landed on, and `dfs_query_then_fetch` does not fix it.** The clause expands the final query token against the per-shard term dictionary, then BM25 sums IDF across EVERY expansion. Two documents that are equally good matches score differently because their shards hold different word lists. Measured 2026-08-02 on `63 GEOFFREY RD CHITTAWAY POINT`: the range doc's shard also held `POINTERS`, giving it a 9th expansion where the exact doc got 8; that one rare term contributed 12.75 of idf, which was the ENTIRE 61.171-vs-58.268 margin. DFS is the textbook remedy for cross-shard scoring skew and is INEFFECTIVE here (tested, byte-identical results) because the expansion SET is built per-shard before DFS gathers statistics. Pre-exists ADR-041 and is present on the old analyzer identically — ADR-041 only compressed absolute scores ~5x, so constant noise crossed a threshold. Tracked as P078.
- **In a Lucene `_explain`, the number after `in` is an internal doc ID, not a document count.** `weight(sla:63 in 1203037)` means Lucene doc 1203037, NOT "1203037 documents contain this term". Misreading it as a doc count produced a confident, wrong cross-shard-IDF hypothesis that survived a full test cycle before `dfs_query_then_fetch` falsified it. The real term statistics are in the nested `idf, computed as log(1 + (N - n + 0.5) / (n + 0.5))` block, where `n` and `N` are labelled.

- **`match_phrase_prefix` matches a phrase ANYWHERE in a field, not from the start.** Only the final term is treated as a prefix. A sub-unit's `sla` contains its parent's complete token sequence, so under contains-semantics the parent-vs-child discriminator is absent from the text by construction and no scoring adjustment is well-posed. Two prior fixes tuned scores against a question that had no correct answer available to it. `prefix` on a `.raw` keyword subfield is native starts-with and needs no analysis step. ADR-043.

- **A cheap way to test whether a scoring clause is the culprit: make it inert and see if the answer improves.** Under the pre-ADR-043 query a MISTYPED address returned the street-level record first 85% of the time while a correctly typed one got it wrong 60% — typing correctly made the result worse, because a typo made `phrase_prefix` inert (its fuzziness was disabled) and left the working clause to decide. That inversion was stronger evidence for the diagnosis than any `_explain`.

- **A `prefix` on a large keyword dictionary costs whatever it matches, and the cost is selectivity, not length.** `"1"` measured 2651 ms against a 334 ms baseline; `"A"` was FASTER than baseline because almost no SLA begins with a letter; `"10"` is two characters and still cost +191 ms. The trailing space is itself the selectivity — `prefix: '1 '` reaches only street-number-exactly-1 and measures within noise. Gate on "has the user typed past the street number", never on a character count.

- **A field can be mapped, queried, and populated at the wrong path for months without anything noticing.** `sla_range_expanded` is generated correctly and written to `_source.structured.sla_range_expanded` while the mapping declares the top level, so it is populated on 0 of 16.9M production documents and has never been searchable. Three layers were green: a regex asserting the source contains the assignment, a mapping test asserting the field is declared, and Cucumber scenarios that pass via the tokenizer split. **Declaration is not population, and a return-value test would have missed it too** — the loss happens after the mapper returns. Pin end-to-end: what goes into the index is what the query can find. P091.
