# External-Comms Content Rules

What the gate rejects on CONTENT rather than on marker mechanics: em-dashes and absolute traffic counts. Split from `external-comms-and-compendium.md` 2026-08-02 (Tier-3 budget rotation).

- **Draft external-comms prose em-dash-free from the first keystroke — the voice-tone gate FAILs on em-dashes every single time.** `docs/VOICE-AND-TONE.md` bans them in three places (Voice preamble, Terminology > Avoid, Technical constraints) and line 6 scopes the guide to "GitHub issues", so issue bodies and comments are in scope, not just repo files. 2026-07-25: all four upstream reports (P063/P057/P061/P046) FAILed their first voice-tone review on em-dashes alone, costing a full re-review round for each. Substitutions the gate accepts: a colon for an appositive, a comma or full stop for an aside, `1.3.20 to 2.19` for a range. Second recurring FAIL class on the same batch: deictics. "this repo" / "this project's" in a body destined for `windyroad/agent-plugins` resolves to agent-plugins, not addressr — name the repo explicitly. P063's comment took three revisions on that alone.
- **The external-comms gate treats absolute traffic/read COUNTS as confidential traffic-volume disclosure — in commit messages AND code comments.** A read-shadow soak's mirrored-read count over a day was FAILed as a production-traffic-volume figure and had to be scrubbed from both the commit body and the `deploy/main.tf` comments (replaced with "full read coverage, 0 failures"). Doc counts (G-NAF 16.9M) and latency (p95 24ms) pass — they're public-dataset size / performance, not business metrics. Rule: describe soak/traffic qualitatively in committed prose; never commit an absolute request/read count.
