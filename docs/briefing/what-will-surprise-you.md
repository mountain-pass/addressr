## What Will Surprise You

- **A GitHub Actions `workflow_dispatch` input declared `type: boolean` must be compared UNQUOTED in `if:` — `inputs.x == 'true'` silently never matches.** The `inputs` context PRESERVES the declared type (only `github.event.inputs.*` is always-string), and GHA coerces mismatched operands to number: `true == 'true'` becomes `1 == NaN` → false. The failure mode is the worst kind — the run goes **GREEN with the gated step skipped**, so a gate that never fires looks exactly like a gate with nothing to do. Near-miss 2026-07-26: P039's approved Fix Strategy specified the string form for the new `deploy_only` deploy gates; had it shipped, `release.yml`'s publish-free deploy would have been permanently inert and nobody would have seen a red run. Caught by wr-architect, now pinned by `test/js/__tests__/release-workflow-deploy-only.test.mjs`, which fails if anyone re-quotes it. Corollary: on non-dispatch events `inputs` is null, so `inputs.x != true` → true and `inputs.x == true` → false, which is exactly the degradation you want — the boolean form is correct on both paths, the string form on neither.
- **The decisions compendium (`docs/decisions/README.md`) renders only about the first five Confirmation bullets per ADR, so criteria appended at the end of a long `## Confirmation` list never reach the routine architect load surface.** Not a per-bullet character truncation — whole trailing bullets are dropped. Hit 2026-07-26 amending ADR-001: two new criteria added as bullets 6 and 7 (the ones recording that the deploy-only path IS risk-gated) vanished from the compendium entirely, which is precisely the reviewer-invisibility the compendium-refresh discipline exists to prevent. Fix is to COMPRESS rather than append — merge related criteria so the whole set fits, then regenerate and actually read back the rendered `**Confirmation:**` line to confirm each one survived. Reassessment Criteria are excluded from the compendium by design, so body placement there is correct and complete.

- **k6's `http.url` tagged template does NOT percent-encode its interpolated values — and a CI workflow's first real run should never be against master.** The P032 perf probe shipped 2026-07-24 and reddened master on its first nightly (run 30103898200). `` http.url`${BASE_URL}/addresses?q=${query}` `` put a RAW SPACE from `'CHRISTMAS ISLAND'` into the HTTP request line; Node answered a bare 47-byte `400 Bad Request`. The probe had been timing an error path, not the search path. Three reusable lessons: (1) **k6 does not encode for you** — use `encodeURIComponent`; `http.url`'s only job is metric grouping, which an explicit `tags: { name: ... }` already does. (2) **The loudest error line in a CI log is often benign** — the failure was initially blamed on `Error: ENOENT ... Counts.csv`, but `loadGnafData()` explicitly handles a missing `Counts.csv` (the may21+ G-NAF layout has none) and the fixture had in fact loaded 5186 OT rows with the server healthy on `:6060`. Read past the scary line to what actually exited nonzero. (3) **`status === 200` is a near-worthless assertion for a perf probe** — an empty result set is a valid 200 _and is faster than a real search_, so a fixture/index regression makes p95 look BETTER and stays green. Assert on the body. Forensic trick that cracked this one: `data_received ÷ http_reqs` gave 46 B/response, far too small for real headers — that byte count is the signature of a bare protocol-level `400`, which pointed straight at a malformed request line. A 60-second dry run of the k6 script against a 10-line Node stub would have caught all of this before the workflow ever ran.
- **AFK work-problems iter briefings can carry ANOTHER ticket's evaluator caveat — verify against `docs/problems/README.md` Review notes before acting.** The 2026-07-19 P054 iter was dispatched with a CLOSE-CANDIDATE-WITH-CAVEAT citing "driver P007 closed; 3 of 8 tasks; ADR-026 fix in v2.3.0" — all of which describes P015 (see README Review notes), not P054. Acting on the briefing without re-deriving from the ticket file + README would have closed an unfixed upstream defect. Cheap check: the README "Caveated CLOSE-CANDIDATEs" list is authoritative for which ticket owns which caveat.
- The file `client/elasticsearch.js` and all `ELASTIC_*` env vars reference "elasticsearch" but the system actually runs OpenSearch. Historical naming from before the fork.
- **The external-comms gate cannot clear `gh issue create --body-file` — use the quoted-heredoc `--body "$(cat <<'EOF' ... EOF)"` form.** The gate hashes the body it extracts from the command text to match the reviewer's marker; for `--body-file` it extracts an EMPTY draft (gate source: "When absent (npm publish, --body-file...) DRAFT=''"), while the deny message tells you to have the reviewer wrap the full body in `<draft>` — the two keys can never match, so the deny loops forever. The heredoc `--body` form is extracted verbatim and matches a full-body review marker on the first retry. Hit 2026-07-19 filing agent-plugins#368 (two wasted reviewer dispatches before reading the hook source). Same marker-key-mismatch family as the P048 hash-exactness friction (parked, upstream #361). RECURRED 2026-07-20 filing #370, and AGAIN 2026-07-26 filing #395 (third occurrence) — this file is NOT injected into AFK `claude -p` iter subprocesses (the SessionStart briefing surface expects the `docs/briefing/` tree; legacy single-file never migrated — ticketed P062, fix: `/wr-retrospective:migrate-briefing`). Until migrated, AFK iters should grep this file for the relevant gate/tool surface before external-comms work. **Corollary observed 2026-07-26**: editing the draft AFTER a reviewer PASS invalidates the marker hash and re-blocks, and the two gates invalidate independently — a risk-gate re-review does not restore the voice-tone marker. Freeze the draft before dispatching either reviewer. Also: both gates fail CLOSED when handed a `/tmp` path instead of an inlined `<draft>` block (the reviewer cannot read outside the working dir), costing a full round-trip; always inline.
- **The external-comms commit-message gate extracts and hashes only the FIRST `-m` value.** `external-comms-gate.sh` (wr-risk-scorer 0.17.0) `break`s on the first `-m`/`--message` regex match — it does NOT join across multiple `-m` flags. So a multi-`-m` `git commit` gets only the SUBJECT line hashed, while the reviewer (which you hand the full `<draft>`) hashes the whole message → different marker keys → permanent deny-after-PASS. Fix: review the full message, then commit with a SINGLE `-m` holding the entire multi-line body (real newlines, no interior `"`) so the gate's `-m "([^"]*)"` capture matches the reviewed draft. Corollary gap: body paragraphs of a multi-`-m` commit are never leak-scanned. Hit 2026-07-24 committing the P062 park (two denied attempts before reading the hook source). Same marker-key-mismatch family as P048 (parked, upstream #361). **Corollary, 2026-07-26 (three more denies):** the gate hashes the LITERAL text of the `-m` argument as it appears in the bash command, not the string the shell finally passes to git. So a single `-m` is necessary but not sufficient — (a) any apostrophe escaped as `'"'"'` leaves that seven-character sequence in the hashed text while the reviewer saw a plain `'`, and (b) `-m "$(cat msg.txt)"` hashes the literal `$(cat msg.txt)`. Both produce a permanent deny-after-PASS that looks identical to a stale marker. Cheapest fix: **write the commit message apostrophe-free** and pass it as one single-quoted `-m`, so the shell literal and the reviewed draft are byte-identical. To confirm a key before burning a reviewer dispatch, source `hooks/lib/external-comms-key.sh` from the installed wr-risk-scorer and run `compute_external_comms_key "$(cat msg.txt)" git-commit-message` against the marker filenames in `${TMPDIR}/claude-risk-<session-id>/`.
- **Draft external-comms prose em-dash-free from the first keystroke — the voice-tone gate FAILs on em-dashes every single time.** `docs/VOICE-AND-TONE.md` bans them in three places (Voice preamble, Terminology > Avoid, Technical constraints) and line 6 scopes the guide to "GitHub issues", so issue bodies and comments are in scope, not just repo files. 2026-07-25: all four upstream reports (P063/P057/P061/P046) FAILed their first voice-tone review on em-dashes alone, costing a full re-review round for each. Substitutions the gate accepts: a colon for an appositive (`` `@windyroad/itil`: the evaluate-relevance shape set ``), a comma or full stop for an aside, `1.3.20 to 2.19` for a range. Second recurring FAIL class on the same batch: deictics. "this repo" / "this project's" in a body destined for `windyroad/agent-plugins` resolves to agent-plugins, not addressr — name the repo explicitly. P063's comment took three revisions on that alone.
- **One external-comms review per draft, with the `SURFACE:` + `<draft>` structure — a batched multi-draft review produces NO marker and cannot clear any gate.** The PostToolUse mark hook derives the marker key via `derive_external_comms_key_from_prompt`, which regexes a line-anchored `^SURFACE: <name>` plus one `<draft>...</draft>` block, then hashes `sha256(normalize(draft) + '\n' + surface)`. A prompt carrying four drafts and no `SURFACE:` line yields an empty key, so even a PASS marks nothing. Both evaluators (`wr-risk-scorer:external-comms` and `wr-voice-tone:external-comms`) must each be dispatched per draft, SYNCHRONOUSLY (`run_in_background: false` — a backgrounded reviewer never fires its mark hook, P402). Surface names come from the gate's own command matcher: `gh-issue-create`, `gh-issue-comment`, `gh-issue-edit`, `gh-pr-create`, `gh-pr-comment`, `gh-api-security-advisories`, `npm-publish`, `git-commit-message`, `changeset-author`. Any edit to the body after review changes the hash, so both evaluators must be re-run on the exact final text.
- **Releasing needs a manual GitHub Actions approval both times.** The changesets release PR (`changeset-release/master`, "chore: release") has its CI runs gated as `action_required` — a human must approve them in the Actions UI before they run, so `release:watch` stalls waiting for a `build` check that never appears. Approve via the API before merging: `gh api -X POST repos/mountain-pass/addressr/actions/runs/<run_id>/approve` (the run shows `conclusion=action_required` in `gh run list --branch changeset-release/master`). The post-merge Release run on `master` runs automatically (no approval). Hit on both v3.0.0 (#505) and v3.0.1 (#506).
- **`Rolling` on Elastic Beanstalk does NOT mean batched deploys here — two different batching namespaces get conflated, and it has now bitten three documents.** Application deploys use `aws:elasticbeanstalk:command`, where `DeploymentPolicy = "Rolling"` but `BatchSize = "100"` / `BatchSizeType = "Percentage"` puts the whole fleet in ONE batch. The reassuring `MaxBatchSize = 1` / `MinInstancesInService = 2` / `RollingUpdateType = "Health"` values live in a _different_ namespace, `aws:autoscaling:updatepolicy:rollingupdate`, which governs ASG **instance replacement**, not deploys. Quoting the second while talking about the first is the trap: ADR 004 (said `AllAtOnce` outright until the 2026-07-26 amendment), ADR 001, and this briefing line all fell into it. Also note `RollbackLaunchOnFailure = "true"` is `aws:elasticbeanstalk:control` — it covers environment **launch** failure, not a red post-deploy check. 100% Spot; health check targets `/health`. Deploy-window duration is unmeasured.

- **The red-master push guard blocks the very commit that fixes red master.** `push:watch` (and `git push` via the push-gate hook) refuses to push when master's latest CI run concluded `failure` — but a CI-fix commit can only turn master green by being pushed. Chicken-and-egg. Escape: `git push --no-verify origin master` for a commit that only fixes the broken CI (user has authorised this framing explicitly). Hit v3.0.1 when a bad lockfile broke `npm ci`; the fix commit was blocked by the prior red run.

Reconcile from the last committed known-good lock instead: `git checkout origin/master -- package-lock.json && rm -rf node_modules && npx npm@10.9.4 install`, then verify with `npx npm@10.9.4 ci --dry-run` before committing. Match the `packageManager` pin (npm@10.9.4).

Trust CI's check-deps output; defer genuine major migrations via `.dry-aged-deps.json` `exclude` with a reason (the Babel 8 toolchain + `lint-staged` 17 are deferred there now).
