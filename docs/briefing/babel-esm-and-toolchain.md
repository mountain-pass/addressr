# Babel, ESM, and the Build Toolchain

How this repo transpiles, what that breaks, and the Node-version floors that are real versus declared. Split out of `testing-tdd-and-code.md` 2026-08-04 (Tier-3 budget) — that file was carrying test discipline and toolchain quirks together, and the toolchain half grew its own subtopic.

## What You Need to Know

- **`npm run build` exiting 0 does NOT mean the output is loadable.** Babel 8 changed `@babel/preset-env`'s default module handling: with `targets: { node: "current" }` it decides modern Node supports ESM natively and stops transpiling to CommonJS. `lib/` then ships as ESM with extensionless relative imports, which is invalid ESM, and the packaged binary dies at startup with `ERR_MODULE_NOT_FOUND`. The build compiled fine. This reddened master on 2026-08-03, and nothing run locally had loaded `lib/` at all — `test:js` imports from `service/` and `src/` directly. `.babelrc` now pins `"modules": "commonjs"` explicitly. **The check that catches it is packing the tarball and loading it** (`npm pack` → `npm install -g` in a clean container → start the binary), which is what CI's `test:cli2:*` leg does. Compiling and loading are different claims.

- **The `.mjs` tests import untranspiled `.js` service modules, so the test harness floor is Node 22.7, above the declared `engines` floor of `>=22`.** ESM-in-`.js` only loads from 22.7, where module syntax detection landed. On 22.0 the unit suite reports 92 failures out of 216, every one that single cause and none of them real. Shipped code is unaffected because babel emits CJS into `lib/`, which is what operators actually run. `release.yml`'s `engine-floor` job pins 22.7 for this reason and says so in a comment — do not "correct" it to 22.0 to match `engines`.
  <!-- signal-score: 2 | last-classified: 2026-08-04 | first-written: 2026-08-04 -->
- **Raising `engines.node` is a BREAKING change for self-hosted operators, not a warning.** `scripts/check-version.js` runs in `postinstall` and `process.exit(1)`s below the floor, so a bumped floor is a hard install failure. The architect rejected raising it to `>=22.17` purely to silence an `n/no-unsupported-features/node-builtins` lint error on `fs/promises.glob`; a narrow scoped `eslint-disable-next-line` with the reasoning in-file was the right trade instead.
  <!-- signal-score: 2 | last-classified: 2026-08-04 | first-written: 2026-08-04 -->
- **`@babel/node` 8.0.1 is broken upstream and there is no fixed version.** Its bin shim is `import "../lib/babel-node"` — extensionless, inside a `"type": "module"` package, which Node cannot resolve, so `babel-node --version` fails outright. Reproduced in a clean `node:22-alpine` container with only `@babel/node` + `@babel/core` installed. Every `babel-node X` invocation moved to `node -r @babel/register X` (20 npm scripts plus two in `perf-regression.yml`) and the package was removed. If you see `babel-node` reappear in a script, that is a regression.
  <!-- signal-score: 2 | last-classified: 2026-08-04 | first-written: 2026-08-04 -->
- **`service/address-service.js` uses babel-only bare imports** (`import { ... } from '../client/elasticsearch'` with no `.js` extension), so raw Node ESM tests cannot import it. Workaround: extract testable pieces into a sibling clean-ESM module. Precedents: `service/gnaf-package-fetch.js`, `service/covered-states.js` (P034), and `service/gnaf-directory.js` (2026-08-03) — all use `.js` extensions and DI parameters and are importable directly under `node --test`. This extract-to-test-it move is now the standard response to "the branch I need to cover is inside address-service.js".
  <!-- signal-score: 2 | last-classified: 2026-08-04 | first-written: 2026-07-28 -->
- **ESLint 10 changed global-ignores semantics.** Under ESLint 9 a bare `{ ignores: [...] }` config object applied globally; under 10 it does not, and `lib/**` fell back into scope — the transpiled build output alone reported 2604 problems, 78% of the tree-wide total, all noise. Use `globalIgnores()` from `eslint/config`. Also normalise the globs: `lib/**/*` did not match, it needed `lib/**`.
  <!-- signal-score: 2 | last-classified: 2026-08-04 | first-written: 2026-08-04 -->
- **A from-scratch lockfile regen (`rm -rf node_modules package-lock.json && npm install`) can pass `npm install` locally but fail CI's `npm ci`.** Reconcile from the last committed known-good lock instead, and verify with `npx npm@10 ci` before committing. Match the `packageManager` pin. Corollary learned 2026-08-03: npm 10's ERESOLVE can report a self-contradictory conflict (`@babel/core@8.0.1` "conflicting" with a peer of `^8.0.0`) when the lockfile is stale relative to a coordinated multi-package bump. That message is the resolver confused by the old tree, not a real constraint — the real blocker was elsewhere (an unreferenced `@babel/plugin-proposal-class-properties` peering on `@babel/core ^7`). Read past the reported pair to find a package that genuinely pins the old major.
