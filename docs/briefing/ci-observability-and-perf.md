# CI Observability and Perf Measurement

Whether the pipeline is telling you the truth, and what the perf harness can actually resolve. Split out of `releases-and-ci.md` 2026-08-04 (Tier-3 budget).

## What You Need to Know

- **A watcher that allow-lists job names goes stale the moment a job is added, and reports GREEN when it does.** `push:watch` printed "Push pipeline completed successfully" while both `build-and-test` matrix legs were red on 2026-08-03 — that is how a Babel 8 regression sat on master unnoticed. Three compounding defects: it selected a job named `build` that `release.yml` does not have; it selected the exact name `build-and-test` while a matrix names its jobs `build-and-test (2.19.5)` and `(3.5.0)`; and it tested only for the literal `"failure"`, but when a leg fails `release` never runs and concludes `skipped`. `gh run watch` was also invoked `|| true`. `release-watch.sh` carried the same class, plus a PR-check selector on the non-existent `build` job that made its "no build check found, proceeding" branch fire on every run — a red release PR was never caught and the 60-second wait was theatre. Both now allow-list NOTHING: every job is enumerated and anything not `success` or `skipped` fails, with `check-deps` the single ADR-015 exemption, and an empty scan is UNKNOWN rather than a pass. **Verify a run directly with `gh run view <id> --json jobs --jq '.jobs[] | "\(.conclusion)\t\(.name)"'` rather than trusting a summary line** — that lists matrix-suffixed and newly-added jobs by construction.

- **The k6 regression harness cannot resolve a difference smaller than about 2x, measured.** Ten runs against a local OpenSearch container, alternating between two express versions so drift hit both equally: within-version p95 spread was 3x (19-58 ms) on a quiet machine, while the between-version median difference was 1.8%. The `p95 < 1500 ms` threshold sits ~40x above the observed ~37 ms median — loose, but defensible against that spread; tightening toward the median would flap constantly. **A single A/B pair from this harness is not evidence of anything**: the first two runs, taken in sequence, showed a 34% p95 improvement and 54% throughput gain that vanished entirely once the runs alternated. That was cache warming. Recorded on P032, whose open task asked for exactly this characterisation.

- **k6's `http.url` tagged template does NOT percent-encode its interpolated values — and a CI workflow's first real run should never be against master.** The P032 perf probe shipped 2026-07-24 and reddened master on its first nightly. `` http.url`${BASE_URL}/addresses?q=${query}` `` put a RAW SPACE from `'CHRISTMAS ISLAND'` into the HTTP request line; Node answered a bare 47-byte `400 Bad Request`. The probe had been timing an error path. Three reusable lessons: (1) **k6 does not encode for you** — use `encodeURIComponent`; `http.url`'s only job is metric grouping, which an explicit `tags: { name: ... }` already does. (2) **The loudest error line in a CI log is often benign** — read past the scary line to what actually exited nonzero. (3) **`status === 200` is a near-worthless assertion for a perf probe** — an empty result set is a valid 200 and is faster than a real search, so a fixture/index regression makes p95 look BETTER and stays green. Assert on the body. Forensic trick: `data_received ÷ http_reqs` gave 46 B/response, the signature of a bare protocol-level `400`. A 60-second dry run against a 10-line Node stub would have caught all of this.
