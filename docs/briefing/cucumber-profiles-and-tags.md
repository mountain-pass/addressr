# Cucumber Profiles, Tags, and Step Traps

How the cucumber profiles select scenarios, and the ways a feature file can look present while running never. Split out of `testing-tdd-and-code.md` 2026-08-04 (Tier-3 budget).

## What You Need to Know

- **"The test exists" and "the test runs" are different claims, and only one of them is easy to check.** `cucumber.js` appends `and @rest2` to the tag filter for EVERY profile, so a new `.feature` file without that tag is silently excluded — it sits in the repo, greps as present, and executes never. On 2026-08-03 a feature written specifically to close three unmet ADR-037 Confirmation criteria did exactly that, and the only reason it was caught is that the assertion was deliberately broken and the suite still reported 32/32 green. **Mutation-test any new test before believing it.** Break one assertion, confirm the run goes red, restore. The scenario count moving (32 to 37, 203 steps to 232) is the corroborating signal. This is the same false-coverage shape as the ADR that cited a feature file which did not exist — which is what the new feature was written to fix. The failure reproduces itself if you are not looking.

- **cli2 cucumber profile spawns the origin as a separate preinstalled binary** via `run-p --race start:server2:preinstalled dotest:cli2:nogeo`. Setting `process.env` in a step definition doesn't reach that process. Scenarios that mutate env vars mid-run must be tagged `@not-cli2`. P010 is now a Known Error with guardrail: `scripts/check-not-cli2-tags.mjs` (wired into `npm run pre-commit`) fails any `@not-cli2` tag without a `docs/problems/NNN-` cross-reference in the feature file. Combined `@not-cli @not-cli2` is exempt.
- **The Cucumber `will NOT include:` step at `test/js/steps.js` reads `this.current.json` without the v2 `.content` fallback that the sibling `will include:` step has.** Breaks every v2 scenario that tries to assert an absence. Workaround until the step is fixed: use `1st "item" link is followed` + `returned address summary will be:` to assert the first result positively (which implicitly excludes the unwanted doc from the top slot). Discovered when v2.4.0's ADR 028 mid-range-NOT-false-positive scenario crashed CI with `TypeError: Cannot read properties of undefined (reading 'find')`.
- **The profiles are generated, not written — read `cucumber.js` before adding a feature file.** `generateConfig(profile)` builds every profile's tag expression, and for `rest2` / `cli2` / `nodejs` it appends `and @rest2`. It also swaps the feature glob for a `@cucumber-<profile>.rerun` file whenever that file is non-empty, which silently narrows a run to the previous failures. A run whose scenario count dropped without explanation is almost always a stale rerun file: clear them (`: > @cucumber-*.rerun`) before trusting any A/B measurement. Cost a discarded 19-scenario result during the express 5 comparison, 2026-08-03.

- **A feature that builds its own app cannot run in the `rest2` or `cli2` profiles.** Those profiles already have a live origin — `rest2` an in-process one started in `BeforeAll`, `cli2` a separately spawned binary. Calling `buildRest2App()` alongside the running server was measured to break the rest2 run: 38 scenarios and 234 steps green became a hard timeout on an unrelated locality scenario, and reverting the tag restored it. In `cli2` it would be worse than broken — it would PASS while asserting against an in-process app that is not the binary under test. Tag such features `@rest2 @not-rest2 @not-cli2`; the embedded profile builds a fresh app per scenario by design, which is what they need. This is why ADR-037's CORS preflight scenarios live in the embedded tier.
