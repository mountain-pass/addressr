# Agent Behaviour and ITIL Workflow Patterns

Recurring assistant failure modes (asserts-without-verifying, hypothesis-heavy) and problem/ADR workflow traps. Split from `what-will-surprise-you.md` 2026-07-28 (Tier-3 budget).

- **A note in a config file is not evidence, and this repo's deferral notes were wrong three times in one day.** `.dry-aged-deps.json` carried sixteen `exclude` entries, each with a reason. Checking rather than repeating them: "Babel 8 toolchain migration deferred" was blocking thirteen packages, but `@babel/eslint-parser@8` peers on `^9.0.0 || ^10.0.0` and every other eslint plugin already accepted eslint 10 — the real blocker was one unreferenced `@babel/plugin-proposal-class-properties`. Express's "significant API breaking changes" held zero uses of any removed express 5 API. `dry-aged-deps` named a depcheck parent bump for a `brace-expansion` advisory, but depcheck was already on its newest published version so that route did not exist. All sixteen exclusions are now gone. **I repeated the first of these as fact in my own commit message before testing it.** When a note explains why something cannot be done, treat it as a hypothesis with an author and a date, not as a finding — especially when it is the only thing standing between you and a large amount of blocked work.

- **A subagent will report STAGED-BUT-UNCOMMITTED prose as established fact.** On 2026-08-02 a hang-off-check agent reported "the ADR-041 cutover landed 2026-08-01", citing a P073 sentence that was an anticipatory edit sitting in the index, not yet committed and not yet true — production was still serving the old domain and the inbound defect was still live. Subagents read the working tree, which contains what you INTEND as readily as what happened. When a subagent asserts a fact about world state (something is deployed, released, closed, applied), verify against the world (`curl` the endpoint, `git log`, `gh run list`) rather than against the repo. The corollary is to write anticipatory prose in the future or conditional tense until the thing is true, because whatever is staged is what the next agent will believe.
- **Guessing a mechanism costs more than reading the evidence, and a wrong guess can survive a full test cycle.** Three consecutive wrong hypotheses on one ranking defect (score bucketing, de-boosting the wrong field, per-shard IDF fixable by DFS) before reading the complete `_explain` tree, which gave the answer in one pass. The third guess was built on misreading a number in output that had been on screen the whole time. When output is truncated or skimmed, the cheap move is to print the whole structure once rather than to form a hypothesis from a fragment and spend a test cycle on it.
- **Opus sometimes invents diagnoses when reasoning from commit-message evidence alone.** The e7c9c37 recovery commit's "lint-staged dropped the file because it's not in the match globs" was authored by Opus without running an experiment — it shaped P011's entire initial description. Lesson: for commit-after-the-fact diagnoses, require a literal replay before trusting the commit message as source-of-truth. Memory `feedback_lint_staged_changeset.md` warns about this.
- **Opus tends to open problem tickets hypothesis-heavy before probing live.** P017 opened with 5 candidate causes before a single probe had run; live probes (direct backend vs. RapidAPI edge) produced the actual root cause in two curls. Preferred order: probe → state hypothesis with evidence → write failing test → open ticket with evidence.
- **Opus ships designs that invent domain semantics without validating with the user.** ADR 026 shipped `sla_range_expanded` with full-range interpolation (aliases for every number between first and last). The user immediately corrected: Australian addressing convention says endpoints only. Supersession was required (ADR 028) and v2.3.0 shipped briefly with the defective behaviour. Pattern: when a design rests on a domain assumption (addressing convention, scoring intent, persona workflow), surface the assumption explicitly in the ADR's Context section and ask the user before writing the Decision Outcome.
- **Opus writes ticket/ADR prose claiming production infra topology without checking `.env` or `deploy/main.tf` — even when the briefing already gives the answer.** On 2026-04-21, P028's initial description asserted addressr self-hosts `opensearchproject/opensearch:1.3.20` via EB Docker; the user corrected: production is AWS-managed OpenSearch Service (as the briefing "What You Need to Know" has said all along). Required a second commit to fix the ticket. Specific mitigation: when any new doc content names a backend, cluster, image, or hostname, open `.env` and `deploy/main.tf` first and re-scan the briefing before drafting the claim.
