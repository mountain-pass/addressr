# Agent Behaviour and ITIL Workflow Patterns

Recurring assistant failure modes (asserts-without-verifying, hypothesis-heavy) and problem/ADR workflow traps. Split from `what-will-surprise-you.md` 2026-07-28 (Tier-3 budget).

- **A subagent will report STAGED-BUT-UNCOMMITTED prose as established fact.** On 2026-08-02 a hang-off-check agent reported "the ADR-041 cutover landed 2026-08-01", citing a P073 sentence that was an anticipatory edit sitting in the index, not yet committed and not yet true — production was still serving the old domain and the inbound defect was still live. Subagents read the working tree, which contains what you INTEND as readily as what happened. When a subagent asserts a fact about world state (something is deployed, released, closed, applied), verify against the world (`curl` the endpoint, `git log`, `gh run list`) rather than against the repo. The corollary is to write anticipatory prose in the future or conditional tense until the thing is true, because whatever is staged is what the next agent will believe.
- **Guessing a mechanism costs more than reading the evidence, and a wrong guess can survive a full test cycle.** Three consecutive wrong hypotheses on one ranking defect (score bucketing, de-boosting the wrong field, per-shard IDF fixable by DFS) before reading the complete `_explain` tree, which gave the answer in one pass. The third guess was built on misreading a number in output that had been on screen the whole time. When output is truncated or skimmed, the cheap move is to print the whole structure once rather than to form a hypothesis from a fragment and spend a test cycle on it.
- **P011 was misdiagnosed and is now a Known Error with corrected cause.** The ef66d39 release-without-version-bump was NOT lint-staged dropping the changeset — literal replay with the same lint-staged 16.4.0 + same fileset retains `.changeset/*.md` (matches via `*.md` basename pattern, prettier re-stages). Real cause: the changeset was never staged before commit (likely `git add -u` or a miss). Guardrail: `git show --stat HEAD | grep .changeset/` after any release-intent commit + regression test at `test/precommit/changeset-preservation.test.mjs`.
- **Opus sometimes invents diagnoses when reasoning from commit-message evidence alone.** The e7c9c37 recovery commit's "lint-staged dropped the file because it's not in the match globs" was authored by Opus without running an experiment — it shaped P011's entire initial description. Lesson: for commit-after-the-fact diagnoses, require a literal replay before trusting the commit message as source-of-truth. Memory `feedback_lint_staged_changeset.md` warns about this.
- **Opus tends to open problem tickets hypothesis-heavy before probing live.** P017 opened with 5 candidate causes before a single probe had run; live probes (direct backend vs. RapidAPI edge) produced the actual root cause in two curls. Preferred order: probe → state hypothesis with evidence → write failing test → open ticket with evidence.
- **Opus ships designs that invent domain semantics without validating with the user.** ADR 026 shipped `sla_range_expanded` with full-range interpolation (aliases for every number between first and last). The user immediately corrected: Australian addressing convention says endpoints only. Supersession was required (ADR 028) and v2.3.0 shipped briefly with the defective behaviour. Pattern: when a design rests on a domain assumption (addressing convention, scoring intent, persona workflow), surface the assumption explicitly in the ADR's Context section and ask the user before writing the Decision Outcome.
- **Opus writes ticket/ADR prose claiming production infra topology without checking `.env` or `deploy/main.tf` — even when the briefing already gives the answer.** On 2026-04-21, P028's initial description asserted addressr self-hosts `opensearchproject/opensearch:1.3.20` via EB Docker; the user corrected: production is AWS-managed OpenSearch Service (as the briefing "What You Need to Know" has said all along). Required a second commit to fix the ticket. Specific mitigation: when any new doc content names a backend, cluster, image, or hostname, open `.env` and `deploy/main.tf` first and re-scan the briefing before drafting the claim.
- **AFK work-problems iter briefings can carry ANOTHER ticket's evaluator caveat — verify against `docs/problems/README.md` Review notes before acting.** The 2026-07-19 P054 iter was dispatched with a CLOSE-CANDIDATE-WITH-CAVEAT citing "driver P007 closed; 3 of 8 tasks; ADR-026 fix in v2.3.0" — all of which describes P015 (see README Review notes), not P054. Acting on the briefing without re-deriving from the ticket file + README would have closed an unfixed upstream defect. Cheap check: the README "Caveated CLOSE-CANDIDATEs" list is authoritative for which ticket owns which caveat.
- **Orchestrator-supplied `persona=` / `jtbd=` values at capture are usually the PLUGIN home-repo enum, not this repo's corpus — always validate before writing them into a ticket.** This repo's personas are `addressr-maintainer / ai-assistant-user / data-quality-analyst / self-hosted-operator / web-app-developer`, and its jobs are JTBD-001/002/003 (web-app-developer), JTBD-100/101 (data-quality-analyst), JTBD-200/201/202 (self-hosted-operator), JTBD-400 (addressr-maintainer). The `agent-plugins` home repo uses `developer / plugin-developer / tech-lead / plugin-user` with JTBD-001 "enforce governance" and JTBD-006 "AFK". The IDs **collide with different meanings**: this repo's JTBD-001 is "search autocomplete addresses", nothing to do with governance. Governance and tooling tickets here anchor to `addressr-maintainer` / `JTBD-400`. Check with `ls -d docs/jtbd/*/ | xargs -n1 basename` before accepting supplied values — this is the P383 adopter-portability rule. Recurred on all three captures of the 2026-07-26 iter (P064/P065/P066 arrived with `plugin-developer` + JTBD-001/JTBD-101), so the leak is systemic to the orchestrator's capture briefing.
- **`/wr-itil:capture-problem` Step 0 halts on pre-existing committed README drift (P041) — even drift the skill itself produced on a prior invocation.** capture-problem deliberately defers README refresh per the lightweight-capture contract (ADR-032); a subsequent capture in the same session then hits the Step 0 halt because the prior capture's deferred refresh is the "pre-existing drift". The override path works (user says "capture anyway"), and `/wr-itil:reconcile-readme` resolves the drift cleanly, but the friction defeats the lightweight-capture design intent.
- **ADR Confirmation wording for problem-lifecycle transitions: tie to criteria, not acceptance.** The `/wr-itil:manage-problem` skill auto-transitions Open → Known Error when root cause + workaround + fix strategy are documented — usually at ADR **proposal**, not acceptance. ADR 029's Confirmation says "P028 transitions on acceptance of this ADR" but the transition happened at proposal. Future ADRs: phrase as "once root cause and fix strategy are documented (i.e. at proposal of this ADR)" to avoid the drift.
- **Parking an upstream-blocked ticket whose upstream issue was filed at the current lifecycle state: reconcile-and-skip the `/wr-itil:update-upstream` dispatch.** The manage-problem Step 7b advisory tells you to post a lifecycle comment on every transition of a `## Reported Upstream` ticket, but when the filing already communicated the confirmed root cause, the comment restates prior as new (the P060 defect, parked upstream as agent-plugins#369). Established pattern, applied on the P053, P054, and P056 parks: re-verify the breach live at park time, record "reconciled-and-skipped per P060" in the `## Parked` section + commit message, post nothing.
