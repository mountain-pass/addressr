# Cutover Mechanics

What actually has to happen for a search-backend cutover or rollback to take effect, and how each step lies to you if you let it. Split from `opensearch-and-deploy-state.md` 2026-08-02 (Tier-3 budget rotation).

- **The EB primary SigV4 config EMPTIES `ELASTIC_USERNAME`/`ELASTIC_PASSWORD`, not just sets `ELASTIC_AUTH_MODE=sigv4`.** `buildClientNode` (`src/client-node-url.js`) omits embedded creds only when username is empty, giving the credential-less node URL the SigV4 signer wraps. Leaving basic creds set alongside sigv4 is an untested config. The cutover EB block: `ELASTIC_HOST=module.opensearch_v2.endpoint`, `ELASTIC_AUTH_MODE=sigv4`, `ELASTIC_REGION=ap-southeast-2`, `ELASTIC_USERNAME=""`, `ELASTIC_PASSWORD=""`.
- **`/health` now pings OpenSearch (503 when unreachable) — a static health check silently breaks zero-outage auto-rollback.** Pre-2026-07-10 `/health` returned 200 without touching the backend, so a misconfigured backend cutover would pass health, roll out fleet-wide, and NOT trigger EB's `RollbackLaunchOnFailure`. `src/es-health.js` (`checkEsHealth`/`checkEsHealthCached`) now `ping()`s the app's `globalThis.esClient`; 503 → EB marks unhealthy after `UnhealthyThreshold=5 × 10s ≈ 50s` → auto-rollback. `HEALTH_ES_PROBE=off` reverts to always-200 (ops kill-switch); a ~5s TTL cache bounds anonymous ping-amplification (`/health` is on the ADR 024 unauth allowlist). General lesson: a deploy-gating health check MUST exercise the dependency it's protecting, or the auto-rollback is theatre.
- **A cutover repoints the SERVING path but you must ALSO repoint every WRITE/refresh consumer.** The 2026-07-10 v2 cutover flipped the EB read path to v2 but the 9 quarterly loader crons kept writing v1 — production read v2 while v2's data silently froze and v1 (unread) kept getting fresh data. The architect caught this before the v1 decommission. When cutting over a backend, enumerate ALL consumers (serving reads, loaders/refreshers, dashboards, alarms), not just the request path.
- **Edge caching MASKS a backend cutover, in both directions.** During the 2026-08-02 rollback drill the EB environment had already flipped to v3 and was Ready/Green, yet the canonical verification query `55 Pyrmont Bri` kept returning the v4 result for several minutes because the response was cached at the edge (`cf-cache-status` on the RapidAPI/Cloudflare path). Reading that, the first conclusion was "the flip did not take effect" — wrong, and in a real incident it is the conclusion that makes you flip again or roll further back. **Verify a cutover with a query that has never been requested**, or add a cache-buster. A never-before-seen partial like `12 Pyrmont Bri` returned 0 immediately and gave the true answer. Corollary: `/health` cannot discriminate either, since it is a `ping()` that goes green against whichever domain is wired.
- **The rollback path is EXERCISED, not assumed — and it costs 6m36s.** The 2026-08-02 drill flipped `ELASTIC_HOST` to v3 and back, discharging ADR-029's "rollback verified to complete within 10 minutes end-to-end" criterion that had sat open and unmeasured across three migrations. Measured push-to-EB-updated: 6m36s. Two things it exposed: v3 is **no longer fed** by the quarterly loader (repointed to `gha_v4_loader` at the cutover), so every G-NAF refresh makes a rollback serve staler data — a second clock on the rollback net independent of decommission; and the edge-cache trap above. Before the drill, this project had surrendered the warm-standby net **twice** without ever exercising it (v1 deleted 2026-07-11, v2 2026-07-14, each an "accepted trade"), so "we'll test it later" had a 0-for-2 record.
