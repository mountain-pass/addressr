# Releases and CI

The changesets release flow, GitHub Actions workflow traps, the push guard, lockfiles, and the risk-appetite commit gate. Split from `what-will-surprise-you.md` 2026-07-28 (Tier-3 budget).

- **A GitHub Actions `workflow_dispatch` input declared `type: boolean` must be compared UNQUOTED in `if:` — `inputs.x == 'true'` silently never matches.** The `inputs` context PRESERVES the declared type (only `github.event.inputs.*` is always-string), and GHA coerces mismatched operands to number: `true == 'true'` becomes `1 == NaN` → false. The failure mode is the worst kind — the run goes **GREEN with the gated step skipped**, so a gate that never fires looks exactly like a gate with nothing to do. Near-miss 2026-07-26: P039's approved Fix Strategy specified the string form for the new `deploy_only` deploy gates; had it shipped, `release.yml`'s publish-free deploy would have been permanently inert and nobody would have seen a red run. Caught by wr-architect, now pinned by `test/js/__tests__/release-workflow-deploy-only.test.mjs`, which fails if anyone re-quotes it. Corollary: on non-dispatch events `inputs` is null, so `inputs.x != true` → true and `inputs.x == true` → false, which is exactly the degradation you want — the boolean form is correct on both paths, the string form on neither.
- **Making a workflow reusable? Move its `concurrency:` off `${{ github.workflow }}` first, or the first `workflow_call` deadlocks.** In a called workflow `github.workflow` resolves to the **caller's** name, not its own. So a callee carrying workflow-level `concurrency: ${{ github.workflow }}-${{ github.ref }}` mints a group byte-identical to a caller carrying the same expression: the caller waits on the callee, the callee queues behind the caller, and the run hangs until it times out. Caught in review 2026-07-26 adding `workflow_call` to `docker-image.yml`, whose group would have collided with `release.yml`'s at stage 3. Fix is a job-level group with a literal prefix (`group: docker-image-${{ github.ref }}`), the shape `reusable-update.yml` already uses; pinned by `test/js/__tests__/docker-image-workflow.test.mjs`. Related trap in the same family: a called workflow's `github.event_name` is also the caller's, which is what lets one `if:` gate serve both the direct-push and the called path.
- **Releasing needs a manual GitHub Actions approval both times.** The changesets release PR (`changeset-release/master`, "chore: release") has its CI runs gated as `action_required` — a human must approve them in the Actions UI before they run, so `release:watch` stalls waiting for a `build` check that never appears. Approve via the API before merging: `gh api -X POST repos/mountain-pass/addressr/actions/runs/<run_id>/approve` (the run shows `conclusion=action_required` in `gh run list --branch changeset-release/master`). The post-merge Release run on `master` runs automatically (no approval). Hit on both v3.0.0 (#505) and v3.0.1 (#506).
- **The red-master push guard blocks the very commit that fixes red master.** `push:watch` (and `git push` via the push-gate hook) refuses to push when master's latest CI run concluded `failure`. Historically escaped via `git push --no-verify origin master` for a CI-only fix — but that override was REMOVED by P377/RFC-029. See the obsolete-dispatch variant + current escape below.
- **The red-master push guard can be blocked by an OBSOLETE `workflow_dispatch` run you triggered earlier — and the escape is a fresh Release run, not `--no-verify`.** P377/RFC-029 removed the `ci-bypass` override, so `push:watch` hard-refuses to push when master's _latest_ CI run concluded `failure`. A manual `gh workflow run "Docker Image"` test that failed (e.g. a since-abandoned Docker Hub cred probe) becomes that latest red run and blocks an unrelated fix — the P052 deadlock via a stale dispatch. Escape (user-authorised 2026-07-28): trigger a fresh `gh workflow run "Release" --ref master`; with no changeset it only builds+tests (docker-publish and deploy both skip), concludes green, becomes the new latest run, and the gate clears.
- **A from-scratch lockfile regen (`rm -rf node_modules package-lock.json && npm install`) can pass `npm install` locally but fail CI's `npm ci`** ("package.json and package-lock.json not in sync", `@types/node` dedup conflict). Reconcile from the last committed known-good lock instead: `git checkout origin/master -- package-lock.json && rm -rf node_modules && npx npm@10.9.4 install`, then verify with `npx npm@10.9.4 ci --dry-run` before committing. Match the `packageManager` pin (npm@10.9.4).
- **`dry-aged-deps` (check-deps) reads live npm-registry publish dates, so local and CI can disagree.** A newly-aged major (Babel 8 crossing the 7-day threshold) was flagged in CI but not locally because the local registry-metadata cache was stale. Trust CI's check-deps output; defer genuine major migrations via `.dry-aged-deps.json` `exclude` with a reason (the Babel 8 toolchain + `lint-staged` 17 are deferred there now).
- **The changesets release flow is gated on `steps.changesets.outputs.published == 'true'`.** Rollback without a working changeset requires adding a trivial patch changeset to trigger a fresh deploy — there is no `workflow_dispatch` shortcut. Keep `gh secret delete` + one-line changeset as the documented rollback for env-var-driven features.
- **`release.yml`'s `Deploy new version` step is gated on `steps.changesets.outputs.published == 'true'`** — `workflow_dispatch` alone doesn't fire `terraform apply`. Every infra-only deploy event must bundle a `.changeset/*.md` (patch bump suffices). ADR 029 Phase 1 ships v2.4.1 (provision), v2.4.2 (tag fix), v2.4.3 (UA fix), v2.4.4 (uppercase fix) so far — each apply event = a release.
- **Addressr releases via the changesets GitHub Action triggered by `git push origin master`**, not via local `npm publish` or `changeset publish`. Those commands run inside the release workflow, not on the developer's machine. Release-gating (pre-release risk checks, voice/tone review of release notes, changeset presence verification) must happen at the push step, not at the publish command. See P021 for the planned pre-push risk blocking hook.
- **`release:watch` script may falsely report "no new version published" even when publish+deploy+smoke tests all succeed.** Verify via `gh run view` logs or npm registry if in doubt.
- **The risk-scorer commit gate blocks commits at 6/25 or higher (appetite = 5).** Not discoverable until you hit it. Mitigation paths in the hook message: split the commit, add risk-reducing measures (`R1..Rn` suggestions in the scorer report), or — for a live incident — re-delegate to `wr-risk-scorer:pipeline` with incident context for a bypass marker. Adding one well-scoped Cucumber scenario frequently shaves 1-2 points and gets below appetite. **CAVEAT (2026-07-14): the `wr-risk-scorer:pipeline` AGENT mis-states this as "above appetite (>4)" and returns STOP on a residual of 5 — but the actual gate (`risk-gate.sh` parses `Threshold: 5` from RISK-POLICY.md, denies only `score > 5`) PASSES a 5.** So a 5/25 is WITHIN appetite; do NOT escalate it with a bypass or an AskUserQuestion. Only 6+ blocks. When the scorer says "above appetite" on a 5, restate it correctly and proceed.
- **The honest way past an above-appetite cutover is to EXERCISE the un-exercised scenario, not bypass it.** The v2→v3 cutover scored 8/25 because the scorer floored likelihood on "full-primary-concurrency untested" (read-shadow only mirrors low-volume reads). Running the ADR-031 k6 leg for real — local `addressr-server` pointed at the candidate domain over SigV4, sustained 20 VUs (0 failures, p95 368ms) — closed that exact gap and dropped the residual to 4 (within appetite) with no bypass. Reusable: when a score is driven by an un-exercised failure mode, run the test that exercises it.
- **k6's `http.url` tagged template does NOT percent-encode its interpolated values — and a CI workflow's first real run should never be against master.** The P032 perf probe shipped 2026-07-24 and reddened master on its first nightly. `` http.url`${BASE_URL}/addresses?q=${query}` `` put a RAW SPACE from `'CHRISTMAS ISLAND'` into the HTTP request line; Node answered a bare 47-byte `400 Bad Request`. The probe had been timing an error path. Three reusable lessons: (1) **k6 does not encode for you** — use `encodeURIComponent`; `http.url`'s only job is metric grouping, which an explicit `tags: { name: ... }` already does. (2) **The loudest error line in a CI log is often benign** — read past the scary line to what actually exited nonzero. (3) **`status === 200` is a near-worthless assertion for a perf probe** — an empty result set is a valid 200 and is faster than a real search, so a fixture/index regression makes p95 look BETTER and stays green. Assert on the body. Forensic trick: `data_received ÷ http_reqs` gave 46 B/response, the signature of a bare protocol-level `400`. A 60-second dry run against a 10-line Node stub would have caught all of this.
